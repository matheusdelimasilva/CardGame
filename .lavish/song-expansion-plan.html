The change that unlocks scale

Discover albums, then verify tracks. The current pipeline mostly starts from song articles and chart rows. Artist discographies and original album tracklists expose many songs it never sees. Recovering all 83 existing misses from 1960–1999 would still leave most of the deficit.

Recommended: mostly automatic

Automate discovery, strong recording matches, deduplication, previews and export. Review uncertain versions and release dates. This can reach hundreds without treating ambiguous matches as verified.

Fully unattended subset

Accept only entries with strong recording links, supported dates, compatible credits/version/duration and working previews. Produce a queue for everything else. Volume depends on how much evidence sources supply.

Guardrails that protect the game

Preserve saved-game song keys. Store release evidence and recording identity separately. Never interpret the ISRC assignment year or a compilation release date as the original year. Balance new entries across artists and styles; avoid filling quotas with obscure tracks from a few albums.

Archive bulk APIs are unverified; start with bounded, cached imports. Honor MusicBrainz's shared request limit and provider throttling. A local resumable Node pipeline is enough for the first campaign.

# Brazilian song expansion: hundreds of additions

Plan prepared 2026-11-15 from the current catalog and pipeline. This is a proposal, not an executed import. Targets are additional unique playable recordings, after deduplication and release-year checks.

## Recommendation and measurable goal

Build a mostly automated discovery and verification pipeline, with a small review queue for ambiguous recordings. First aim for **20 playable songs in every year from 1960 through 2026**. That requires **547 net additions** at the current baseline; 490 are needed in 1960–1999. The pool would grow from 1,340 to at least 1,887 if all deficits are filled without removals. A second pass to 25 per year requires 799 total additions from today's baseline, reaching at least 2,139. These are calculated deficits, not a guarantee that every candidate exists on Deezer.

This is a floor per year, not a cap: retain the existing larger years. Prioritize years with the largest deficit. Filling the gaps improves variety; uniform sampling of individual songs will still favor larger years. Sampling changes are a separate product decision.

## Why the current approach does not scale

The current list has 1,713 rows, of which 1,340 have Deezer IDs. It mainly discovers songs through Wikipedia song articles and chart lists. Album tracks without their own article are largely invisible. The 1960s–1990s have only 83 existing rows without IDs (8, 5, 27 and 43 by decade), so even recovering every one cannot fill the 490-song deficit there.

The MusicBrainz step searches recordings for already-known titles; it does not enumerate artists' releases and tracks. Only 712 keys are cached in the local MusicBrainz file, including historical keys. The builder retains supplied curated/category years and only uses MusicBrainz to add an ID for those rows. This does not independently verify those years. The Deezer CLI skips cached null results indefinitely; failed matches need an explicit, versioned retry mechanism. It stores IDs and text, not recording provenance or preview check results. Existing manually sourced additions also have some provisional recording identities: do not count them as a gold-standard training set without auditing them.

Evidence: `tools/songs/brazil/scrape-br.mjs`, `sources-br.mjs`, `fetch-musicbrainz-br.mjs`, `build-songs-br.mjs`, `tools/songs/fetch-deezer.mjs` and `packages/server/src/deezer.ts`.

## Discovery: albums rather than individual title searches

1. Create a reviewed seed manifest of Brazilian performers, grouped by decade and style. Start with 80–120 acts and 200–300 original albums/singles from 1960–1999; add later releases only where annual quotas are unmet. Cover MPB, samba, bossa nova, Jovem Guarda, rock, soul, sertanejo, forró, brega, axé and regional scenes. Artist nationality/identity needs its own evidence: a release sold in Brazil is not evidence that its performer is Brazilian. Keep historical international entries, but count new Brazilian additions separately.
2. Use MusicBrainz artist → release group → original official release → medium/track → recording traversal. Fetch tracklists in batches by album rather than searching each song from scratch. Persist artist, release-group, release and recording MBIDs and source URLs. Exclude compilations, bootlegs, medleys and later re-recordings as initial discovery sources. A compilation can supply audio only after its recording is linked back to a supported original release.
3. Cross-check album dates and tracklists against Discos do Brasil, IMMuB, artist/label catalogs and archival sources. Build one source adapter at a time; validate access and reuse conditions before assuming a bulk API exists. Do not copy album art, prose or audio into the repository.
4. Rank tracks by hit/single/chart evidence and recognition signals where available, then by annual deficit and artist/genre diversity. Album discovery alone does not establish that every track is a recognizable hit. A proposed initial diversity rule is no more than three new tracks from one album and five from one artist in a decade; relax it explicitly if a year cannot otherwise fill.

Budget an initial 1,500–2,500 distinct candidates. A 25–40% acceptance rate would yield approximately 375–1,000 additions; this is a planning assumption to measure in the pilot, not an observed conversion rate. Continue discovery in deficient years until quotas are reached or an evidence-backed gap is reported.

## Verification and automation boundary

Store candidate state separately from the game catalog: `discovered → dated → matched → preview_checked → accepted`, with parallel `needs_review`, `unavailable` and `rejected` outcomes. Retain every rejection reason. Do not let a numerical confidence score override a failed hard check.

**Automatic acceptance requires all of:** a supported performer-specific original release year; a recording-level link to the Deezer version (matching recording ISRC where available, corroborated by release/artist/version metadata); compatible duration (start with a five-second tolerance and send exceptions to review); matching full performer credits; no conflicting live/remix/re-recording tags; no duplicate recording; and a fresh successful audio preview check. An ISRC match is useful evidence, not infallible proof, and its embedded year must never be used as the release year. Conflicting evidence always enters review. Different ISRCs do not necessarily prove different recordings either.

**Review queue:** title/artist-only matches, missing or conflicting ISRCs, remastered/bonus editions, differing release years, incomplete guest credits, duration discrepancies and unlabelled later studio versions. Show original-release evidence beside Deezer album, ISRC, duration, version tags and preview controls. Decisions apply to a specific recording, not an entire artist. Review by album when shared evidence supports several tracks. Keep provisional matches out of the strict accepted count.

**Audio validation:** require a readable track, nonempty preview URL, successful HTTP audio response (200 or 206), audio content type and a nonempty valid audio payload. Check immediately before export; persist time, region/context and result, not the expiring URL or downloaded audio. Retry transient failures with backoff. A failure does not prove global unavailability. Report catalog IDs separately from recently tested previews.

An LLM may suggest candidates, find evidence and summarize conflicts, but must not invent dates, select a recording without evidence or auto-approve its own suggestions.

## Implement in five stages

1. **Baseline and queue foundation.** Add `coverage-br.mjs` with per-year deficits, unique-recording counts and last preview-check status. Add a candidate/evidence schema and `artists-br.json`. Check in accepted evidence; keep bulky HTTP responses in the existing ignored cache. Accepted exports must rebuild with empty network caches.
2. **Recovery and album discovery.** Add `discover-albums-br.mjs` and source adapters. Extend Deezer matching with explicit retry flags (`--retry-misses`, `--older-than`, `--from`, `--to`), full candidate metadata and a matcher-version cache key. Preserve transient errors separately from confirmed misses. Start with the 83 missing IDs in 1960–1999, while discovery supplies the larger pool.
3. **Resolve and review.** Add `resolve-recordings-br.mjs` and `review-br.html` generation, with a decision importer. Reuse the server's strict matcher as one input, enriching it with release/ISRC evidence rather than weakening it. Persist provenance per candidate: source URL and retrieved time, original release and date precision, credited artist, recording MBID, Deezer ID/ISRC/album/duration, decision/reason, preview check time and status.
4. **Pilot before scaling.** Process about 200 candidates spread across 1960, 1965, 1970, 1980, 1990 and 1994. Measure net unique additions, correct-year yield, preview success, automatic acceptance rate and review time. Audit every proposed automatic acceptance in this first pilot. Any wrong recording/year pauses that rule and requires a fix and rerun. Use the measured yield to resize the candidate budget; do not lower verification standards to hit a volume goal.
5. **Scale and publish in batches.** Process 100–200 accepted additions per batch, prioritized by yearly deficits. Generate a diff/report with additions, before/after coverage, artist/genre concentration, evidence conflicts and still-missing years. Validate and ship each batch; stop the first campaign once the 20/year floor is met or remaining years have documented source/availability blockers. Then evaluate the 25/year target.

Suggested commands above are proposed interfaces, not commands available today. A local resumable Node pipeline is sufficient; no hosted infrastructure is needed to prove the workflow. Schedule maintenance only after its behavior and provider access are established.

## Operational limits and validation

Use a single shared MusicBrainz rate limiter across all workers, at least 1.1 seconds between requests, meaningful User-Agent, caching and retry/backoff. Follow provider pagination and dynamically honor throttling; the repository's Deezer 120 ms gap is an implementation setting, not a verified current service guarantee. Probe current Deezer endpoint access in the pilot. If ISRC lookup or other endpoints are inaccessible, retain title-search candidates for review rather than silently auto-accepting them.

Require schema checks, source evidence and decision references, positive IDs, valid years, complete artist credits, duplicate MBID/ISRC/Deezer-ID review, no unexpected deletion/year changes to existing songs, and reproducible offline export. Preserve existing title/artist keys because saved games reference them. Add regression fixtures for original vs live/remix/re-recording, compilation dates, same-title songs, duos/guests and cached null retries. Run the pipeline tests and relevant game/server checks; fix dependency installation before claiming the complete suite passes.

## Fully automatic vs semi-automatic

A fully unattended run can discover, deduplicate, resolve strong identities, test previews, export strict accepted entries and produce a review queue. It cannot guarantee hundreds of historically correct recordings from title/artist matches alone. The recommended workflow automates that bulk work and reviews only the uncertain cases, aiming for **500–800 net additions** across two passes. That range is a goal, dependent on measured yield and access, not a promise. Expect greater review effort for 1960s/1970s compilations. The pilot will establish the actual human workload and runtime; avoid promising a fixed completion date before it.
